## 0. Scope and Non-Goals

**Changed by this document: bytes `0x66`–`0x7F` only (26 bytes, previously all zero).**

- **Not changed:** any field in `0x00`–`0x65` — not one byte
- **Not changed:** `VERSION_ID` (remains `130`)
- **Not defined here:** URI syntax. The sole authority is the ABNF in RFC-002 §10.2; this document adds no syntax
- **Out of scope:** any v1.3.0 kernel or algorithmic material. This document defines **wire format** and **decision rules** only

`MUST`, `MUST NOT`, `SHOULD` and `MAY` are to be interpreted as described in RFC 2119.

---

## 1. The Gap

The §4.1 field table ends at `0x46 AID_ORIGIN` (32 bytes, terminating at `0x66`). The remaining 26 bytes are zero padding. Both existing implementations mark this space explicitly in source:

```python
# DEMO/pulse_header.py
# 0x66..0x80 kept as zero padding (128-byte alignment)
```
```javascript
// DEMO/server.js
// 0x66..0x80 zero padding (128-byte hardware alignment)
```

Meanwhile §10.4 states:

> Dereferencing an `rttp` URI emits **one pulse** — … — carrying `action` as the intent verb.

**There is nowhere to put `action`.** The chain "URI → pulse" is therefore broken at the specification level: the syntax defines a verb, and the frame format has no place to carry it.

This document allocates those 26 bytes, closing the gap **without altering any existing field**.

### 1.1 A Pre-Existing Defect Corrected Here

In the current implementation, `ROUTE_SHARD` is derived from the **pulse sequence number**:

```javascript
// DEMO/server.js (before correction)
const routeShard = crypto.createHash('sha256')
    .update('route_shard_' + pulseSequenceId).digest();
```

⇒ The shard changes on every pulse emitted, so it cannot carry the semantics of a **destination address** — although §4.1 defines it as the "12ns jitter-aligned **Hive navigation hash**". §5 redefines it as derived from the URI `authority`.

## 2. Extension Block Layout

Big-endian, consistent with the fixed region. 26 bytes starting at `0x66`:

| Offset | Size | Field | Notes |
|:---|:---|:---|:---|
| `0x66` | 1 | **`SPEC_REV`** | `0` = pre-v1.2.6 (whole block all-zero); `1` = this revision |
| `0x67` | 1 | **`FLAGS`** | bit0 = `URI_ANCHORED`; **all other bits MUST be 0 in v1.2.6** |
| `0x68` | 1 | **`ACTION_LEN`** | Number of significant `ACTION` bytes; `0` = action omitted |
| `0x69` | 16 | **`ACTION`** | The §10.2 action token, lowercase ASCII, **padded right with `0x00`** |
| `0x79` | 7 | **`RESERVED`** | MUST be zero in v1.2.6 |

```
0x66 0x67 0x68 0x69 ................................... 0x79 ....... 0x7F
[REV][FLG][LEN][        ACTION (16B, NUL-padded)      ][  RESERVED (7B)  ]
```

### 2.1 `FLAGS` bit0 = `URI_ANCHORED`

Set to 1 when this frame's `ROUTE_SHARD` was **derived from a URI `authority`** (§5), rather than from a pulse sequence number or any other local artefact.

> **Implementations performing inter-node routing MUST require `URI_ANCHORED = 1`.**
> When clear, `ROUTE_SHARD` carries no globally routable semantics and MAY be used only for dispatch local to a single switch.

The rule is fail-closed: a shard of unknown provenance must never be used as a global address.

## 3. The `ACTION` Field

### 3.1 Value Space Is Open

§10.2 specifies:

```abnf
action = 1*( %x61-7A / DIGIT / "-" )     ; e.g. vessel / verify / pulse
```

**`action` is an open set, not a closed one.** This document therefore defines **no verb enumeration** — enumerating verbs would convert an open set into a closed one, contradicting §10.2.

### 3.2 Encoding

- Write the §10.2-permitted characters to `0x69` verbatim, as ASCII
- Write the length to `ACTION_LEN`
- Remaining bytes **MUST be `0x00`** (right-padded, no interstitial gaps)
- Maximum length is **16 bytes**; a frame with `ACTION_LEN > 16` **MUST be rejected** in v1.2.6

### 3.3 Omission

`ACTION_LEN = 0` means the action is omitted — i.e. the **default operation** of §10.4 (safe, no side effects).

### 3.4 No Dependency Between `FLAGS.URI_ANCHORED` and `ACTION`

`ACTION` and `URI_ANCHORED` are **independent**: a frame may carry an action without URI anchoring (local dispatch), or be anchored with no action (default operation).

### 3.5 ⚠ Unknown Verbs MUST NOT Be Treated as SAFE

§10.4 declares the **default operation** safe. Because `action` is an open set, a receiver will necessarily encounter verbs it does not recognise.

> **On encountering an unrecognised `action` verb, an implementation MUST NOT infer safety from the "default operation is safe" statement in §10.4.**
> The verb **MUST** be treated as having *unknown* safety, and either require explicit authorisation under the local security policy, or be rejected outright.

Rationale: the "safe" declaration in §10.4 applies to the **omitted-action** form; it is not an endorsement of arbitrary unknown verbs. Treating every unknown verb as "default read" would grant every future verb the safe semantics for free — structurally the same error class as the open-redirect failure mode addressed in §10.6.

## 4. Backward Compatibility

| # | Rule |
|:---|:---|
| **R1** | **Old readers** (pre-v1.2.6) read only `0x00`–`0x65` and **ignore** `0x66`+. Since those bytes were previously zero, **old implementations are compatible with no modification whatsoever** |
| **R2** | A new reader receiving `SPEC_REV = 0` treats `ACTION` as **omitted** ⇒ the §10.4 default operation |
| **R3** | `SPEC_REV = 1` with `ACTION_LEN = 0` is valid, and equivalent to omission |
| **R4** | `ACTION` containing non-§10.2 characters, exceeding 16 bytes, or with non-zero padding ⇒ **MUST reject** |
| **R5** | `SPEC_REV` outside the known set ⇒ **MUST reject** (fail closed) |
| **R6** | `SPEC_REV = 0` with a non-zero extension block ⇒ **MUST reject** (self-contradictory form) |
| **R7** | `SPEC_REV = 1` with non-zero `RESERVED`, or with unknown `FLAGS` bits set ⇒ **MUST reject** |

### 4.1 Why `VERSION_ID` Is Left Alone

Implementing the extension as a `VERSION_ID` increment (e.g. 130 → 131) would cause **old implementations to reject entire frames** (their `verify` compares the version). Interoperability would drop to zero at a stroke. Signalling the extension through `SPEC_REV` instead leaves old readers unable to "see" the new bytes — compatibility comes for free.

## 5. URI → `ROUTE_SHARD`

### 5.1 Rule

```
canonical_authority = intent "." pillar "." root        (lowercase, US-ASCII)
ROUTE_SHARD         = SHA-256( ASCII(canonical_authority) )[0:16]
```

- The **`authority` only**: excluding the scheme, excluding `//`, and **excluding `/<action>`**
- The **first 16 bytes** of SHA-256, exactly filling `ROUTE_SHARD` (u128) in §4.1

### 5.2 Properties

| Property | Meaning |
|:---|:---|
| **Deterministic** | The same authority always yields the same shard (testable) |
| **Pure computation** | No DNS, no registry, no network — consistent with §10.5, *"does not resolve via DNS"* |
| **One-way** | The authority cannot be recovered from the shard (SHA-256 preimage resistance) |
| **Independent of `action`** | Different actions on the same authority ⇒ **the same shard** |

### 5.3 Why `ACTION` Must Exist as a Separate Frame Field

The last row of §5.2 is the answer: **routing addresses *where*, not *what*.**

Were `action` to participate in shard derivation, `rttp://x.y.z/verify` and `rttp://x.y.z/audit` would become **two different addresses** — splitting "different actions on one identity" into different destinations, and leaving the receiver unable to tell that both pulses originate from the same authority.

⇒ Addressing carries the **destination**; `ACTION` carries the **verb**. This is the structural reason §4.1 requires an independent `ACTION` field.

### 5.4 Forms Rejected

Syntax authority is §10.2. The following are rejected by the reference implementation (13 cases in `negative_uris`):

| Input | Rejection grounds |
|:---|:---|
| `rttp://f3b2a1c4.rttp.aicent/VESSEL` | Uppercase — §10.3 canonical form is lowercase US-ASCII (**no normalise-and-admit**) |
| `rttp://subject@rttp.aicent/vessel` | `userinfo` is undefined (§10.3) |
| `rttp://f3b2a1c4.rttp.aicent/vessel?x=1` | `query` is undefined (§10.3) |
| `rttp://f3b2a1c4.rttp.aicent:443/vessel` | `port` is undefined (§10.3) |
| `rttp://f3b2a1c4.rttp.aicent/` | Trailing slash with empty action — §10.2 requires `action = 1*(...)` |
| `rttp://a.b` | Fewer than three authority segments |
| `https://…` | Not an `rttp` scheme; **there is no fallback** (§10.5) |

> ⚠ **Uppercase is not a "formatting difference" — it is invalid input.** The phrase *normalized to lowercase* in §10.3 describes **canonical writing**, not licence for a parser to silently normalise and admit. Doing so would map two distinct strings onto one address, breaking the "one authority, one address" property.

## 7. Decisions

### D1 — `PILLAR` / `ROOT` are not carried as separate fields

They are folded into `ROUTE_SHARD`, which is all routing requires.
*Revisit if and only if* observability without URI parsing becomes a requirement; the space is available in `RESERVED`.

### D2 — `action` longer than 16 bytes is rejected

No extension-verb mechanism is defined in v1.2.6; whether one is needed depends on whether §10.2 ever permits a longer `action` token.

### D3 — `authority` checksum postponed

A frame currently cannot self-certify that its shard corresponds to a given authority. The 7 reserved bytes are provisioned for this in a future revision.

### D4 — `SPEC_REV` increment policy

Increment on any **change of meaning for already-allocated bytes**. Adding new fields *within* `RESERVED` may retain `SPEC_REV = 1`.

### D5 — `URI_ANCHORED` downgrade policy

Unanchored shards **MAY** be used for dispatch within a single switch, but **MUST NOT** be treated as globally routable.
